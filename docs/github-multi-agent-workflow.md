# GitHub 다중 에이전트 개발 워크플로우

이 문서는 채택 진행 중인 운영 방식이자 effort-router 스킬 계약 위의 저장소 기반 워크플로우 계층 — 스킬 계약을 대체하지 않는다.

저장소 기반 다중 작업 개발·운영 원칙. 전체 에이전트 공통 지침 체계 반영 여부 — 2026-11-13 이 환경(Effort-Router 저장소·WSL 기준) 실측에서 미반영으로 확인됨, 타 환경 반영 여부는 판정하지 않음(아래 "반영 위치" 참고). 요약: **PRD 뼈대 → Task 1 시범 → 워크플로우 위임**(킹크랩 요약).

## 원칙

1. **저장소를 GitHub에 연결한다** ("일단 깃연결부터"). 이슈와 PR을 쓰려면 원격 저장소가 있어야 한다.
2. **PRD를 2~3시간 공들여 작성한다.** 가장 중요한 기준은 task끼리 같은 코드 영역이 겹치지 않게 나누는 것(Jake 기준). 건드리는 파일과 폴더가 서로 다르면 병렬 작업해도 충돌이 없고 머지할 때도 쉽다.
3. **Task 1은 직접 꼼꼼하게 시범을 보인다.** 세부 항목을 빡세게 작성하고 항목별로 PR을 하나씩 전부 올린다. 브랜치 이름, 커밋 단위, PR 크기와 본문 형식 등 "이 주인은 이런 식으로 일하는구나"라는 본보기가 된다.
4. **Task 2부터는 "워크플로우대로 해라"로 위임한다.** AI가 Task 1의 패턴을 따라 세부 항목 작성, 구현, PR 열기까지 스스로 진행한다.
5. **중간 수정 사항은 GitHub 이슈로 등록한다.** 작업 흐름을 끊지 않고, 생각날 때마다 핸드폰 GitHub 앱으로 남겨 두었다가 나중에 처리한다.
6. **세분화 자체도 AI에게 시킨다.** "task 세분화해, 우리 워크트리 최대한 이용해서 작업할 거야" → git worktree로 병렬 작업 가능한 단위로 분해. 워크트리는 한 저장소에서 브랜치별로 작업 폴더를 따로 두는 기능이라 영역이 안 겹치는 task를 여러 에이전트가 동시에 진행할 수 있다.

## 단계 요약

| 단계 | GitHub에서 하는 일 |
| --- | --- |
| 준비 | 저장소 연결 |
| 설계 | PRD 작성 (영역이 안 겹치게 task 분리) |
| 시범 | Task 1을 항목별 PR로 직접 올림 |
| 위임 | Task 2부터 같은 방식으로 AI가 PR 생성 |
| 보완 | 떠오르는 수정 사항은 이슈로 등록 |

## 보완 규칙

- **겹침 해결 기준**: 영역이 겹칠 수밖에 없는 task도 병합 순서·단독 담당·기준 파일 같은 해결 기준을 미리 만들어 두면 병렬 처리 가능한 범위가 늘어난다.
- **Git hook**: 작성 중 발생하는 이런저런 문제는 깃훅으로 간단하게 예방되는 경우가 많다. 반복 실수·충돌은 훅으로 커밋 시점에 잡는다.
- **PR 리뷰 자동화**: [alibaba/open-code-review](https://github.com/alibaba/open-code-review)는 **main 병합할 때만** 사용. (2026-11-13 실측: 링크 존재 확인 HTTP 200)
- **CI 전략**: PR마다 CI를 돌리면 PR이 많을 때 느리다. **로컬에서 PR 단위 CI → GitHub는 묶음 단위 CI**만.

## effort-router 스킬 계약 대응

이 문서의 개념이 effort-router 스킬 계약(§·r 표기)의 어떤 계층에 대응하는지의 지도다.

| 워크플로우 개념 | Effort-Router 계약 대응 |
|---|---|
| 저장소 GitHub 연결(원칙 1) | 스킬 계약 직접 대응 없음 — 원격 저장소·이슈/PR 인프라 전제 |
| PRD 영역 분리(원칙 2) | §5 얇은 계획(깊이는 위험에 비례) — 다중 기록자 겹침은 트리 소유 게이트(r27) 조율 |
| 항목별 PR·Task 1 시범(원칙 3) | §5 PR 분할 계약 — 직렬 상한 5 PR(강제)·목표 2-3 PR |
| Task 2 위임(원칙 4) | §2 라우팅 테이블 ③구현 역할 화이트리스트 — 위임은 메인 중심·서브는 라우터 재호출 금지(어휘 '계층적 위임'). ●●● 팬아웃은 ②검토 렌즈 병렬 전용이라 구현 위임 대응 아님 |
| 이슈 등록(원칙 5) | §5 범위 밖 기여 분리 — 작업 흐름을 끊지 않고 접수, 후속 개선 섹션으로 나중에 처리. 이슈·PR 조작 자체는 §3 외부 효과 멱등(영수 보고) |
| 워크트리 병렬(원칙 6) | 워크트리 수명주기 게이트(r24) — create·done(완료 제거 의무, 호출 주체 메인 단일), 팬아웃은 하위 task-id별 create |
| PR 리뷰·open-code-review(보완 규칙) | ④리뷰(review-pr-*)가 1차 — merge 판정 권한은 메인 세션(§4). 도구는 main 병합 시점 보조 |
| Git hook(보완 규칙) | r28 격리 가드 — 타 세션 활성(alive) claim 공존 시에만 전체 스테이징 패턴(pathspec 없음) 커밋 차단·pathspec 지정 커밋은 허용(단독 세션 무간섭)·본 저장소 국소 선택 어댑터(미러 환경 미작동). 사용자 git 훅은 이 가드 밖 보완 계층 |
| CI 전략(보완 규칙) | §3 증거기반 보고(핵심 테스트 1회 재실행 + 검증 핀 게이트 보강) — verify는 최종 PR 머지 후 수행(§5 PR 분할) |
| 겹침 해결 기준(보완 규칙) | r27 트리 소유 게이트 — claim·check·status 조율(세션·트리 등록·침입 경고). pathspec 커밋 의무·1세션 1트리 원칙은 r28 격리 가드 소속 |

원칙 2 "PRD 2~3시간"·원칙 3 "항목별 PR 전부"는 위 계약의 얇은 계획(위험 비례)·직렬 상한(5)·목표(2-3)과 긴장이 있으나 영역 비겹침=독립 변경=병렬 트랙 구조에서 완화되는 대응이다.

# Hermit Gate — 기존 게이트웨이 통합 설계

이 문서는 사용자 결정, PRD, 기술 설계와 게이트가 적용할 작업 규율을 함께 담는다. 게이트웨이는 4절의 작업 규율을 사용한다.

## 1. 사용자 결정 기록

| 결정 | 근거·영향 | 결정을 바꿀 때 |
|---|---|---|
| 기존 게이트웨이에 Hermit Gate를 상주 기능으로 추가한다. | 게이트웨이가 실행되는 동안 기존 작업 진입점에서 규칙을 적용한다. | 통합 대상이 바뀌면 PRD 적용 범위와 기술 설계의 연결 지점을 갱신한다. |
| 요청 범위 안에서 되돌릴 수 있는 선택은 에이전트가 맡는다. | 작업을 이어가면서 결과에 영향을 주는 결정을 확인하고 수정할 수 있다. 상충하는 명시 요구, 기존 승인 규칙, 범위 변경이나 별도 권한이 필요한 조치는 해당 행동만 보류한다. | 게이트의 보류 조건과 사용자에게 표시하는 항목을 갱신한다. |
| 첫 작업에서 맥락을 배우고, 실제 명칭과 순서는 대상 저장소에서 확인한다. | 시범 작업의 목적·범위·선행 관계는 후속 설계의 근거가 된다. 새 작업의 이름과 순서는 현행 저장소 규칙과 실제 의존 관계에서 결정한다. | 저장소 지침이나 승인된 요구사항이 바뀌면 영향을 받는 설계와 작업 계획을 갱신한다. |
| 기본 브랜치에 병합된 고유 PR 25개마다 감사한다. | 요청한 20~30개 범위에서 정한 현재 기본값이다. 감사 착수 시 일반 병합만 잠시 보류하고, 영향 범위가 확인되면 해당 변경만 보류한다. | 적용 규율과 게이트의 누적 기준을 함께 갱신하고, 변경 시점의 집계 기준을 기록한다. |

사용자가 바꿀 만한 결정은 **결정 → 근거·가정 → 영향 → 수정할 위치** 순서로 기존 작업 기록에 남긴다. 진행·완료 보고에서 해당 결정과 기록 위치를 보여준다. 사용자가 결정을 바꾸면 변경 이유를 덧붙이고 관련 작업을 갱신한다.

## 2. PRD

### 목표와 적용 범위

여러 에이전트가 기존 게이트웨이를 통해 같은 저장소에서 작업할 때, 설계가 원래 요구와 용어를 따르고 여러 작업이 같은 파일을 동시에 수정하는 일을 예방한다. 사용자는 작업마다 승인하는 대신 결과에 영향을 주는 결정을 검토할 수 있다.

적용 범위는 게이트웨이가 식별하고 제어할 수 있는 작업이다. 외부에서 직접 실행되는 Git 작업이나 PR 병합의 차단 범위는 기존 저장소 훅과 호스팅 서비스의 병합 설정으로 결정된다.

### 요구사항과 수용 조건

| 시점 | 요구사항 | 수용 조건 |
|---|---|---|
| PRD 작성·개정 | 저장소 지침과 소유주가 지정한 첫 작업을 읽고 목적·범위·선행 관계를 반영한다. 명칭은 현행 규칙을 따른다. | 시범에 있던 고유 파일명이나 작업 순서가 근거 없이 새 설계에 복제되지 않는다. 영향이 작은 가정은 기록하고 작업을 계속할 수 있다. |
| task 분할·위임 | 변경 경로와 선행 작업을 확인한다. 병렬 task마다 전용 Git worktree를 사용하고 공유 경로의 담당자나 순서를 정한다. | 같은 경로 또는 상위·하위 경로에 대한 두 동시 요청이 모두 쓰기 권한을 얻지 않는다. 관련 없는 task는 진행한다. |
| 커밋·PR 생성 | 커밋은 스테이징된 변경, PR은 대상 브랜치와 비교한 전체 변경을 범위와 대조한다. 달라진 모듈 간 참조에는 기존 의존성 검사나 관련 diff 검토를 적용한다. | 경로를 벗어난 변경이나 확인된 계약 위반은 해당 커밋·PR만 보류한다. 파일 이동의 이전·새 경로가 모두 검사된다. |
| 병합 및 누적 감사 | 현재 감사 상태를 병합 직전에 확인한다. 25번째 병합 후 활성 에이전트는 다음 커밋·PR 전에 자기 영역을 확인한다. | 일반 병합은 감사 영향 범위를 파악할 때까지만 잠시 보류한다. 이후 영향 범위 밖의 PR과 기존 검증·승인을 거친 감사 수정 PR은 진행할 수 있다. |
| 자율 결정과 사용자 검토 | 범위 안의 되돌릴 수 있는 선택은 기본적으로 진행하고 결과에 영향이 있는 결정만 기록한다. | 사용자가 작업 보고에서 결정과 수정 위치를 찾을 수 있다. 사용자 확인이 필요한 결정이 있어도 독립적인 작업은 이어진다. |

## 3. 기술 설계

### 게이트웨이 연결

1. **시작 시.** 기존 게이트웨이의 초기화 과정에서 Hermit Gate를 연결한다. 4절의 작업 규율을 기준으로 삼고, 명칭·경로·절차는 적용 대상 저장소의 지침과 설정에서 확인한다.
2. **작업 직전.** 기존 작업 접수·위임·저장소 작업 처리 경로에서 작업 종류, 저장소 식별자, task, 기준 커밋과 필요한 변경 정보를 게이트에 전달한다. 판정은 진행, 해당 행동 보류, 사용자 결정 필요로 표현한다. 보류 시 이유와 재개에 필요한 조건을 함께 돌려준다.
3. **기록.** 경로 배정과 해제는 기존 공유 작업 기록에서 처리한다. 동시 배정이 가능하면 중복 확인과 배정 기록을 같은 처리 단위에 둔다. 작업 완료나 취소 시 배정을 해제한다. 사용자에게 보일 결정은 기존 작업 이력이나 결정 기록에서 조회할 수 있게 한다.
4. **병합과 복구.** 저장소의 실제 병합 기록으로 고유 PR을 집계하고 현재 감사 기준점과 영향 범위를 저장한다. 기존 병합 대기열이나 담당자가 병합 직전 상태를 확인하고 순서를 관리한다. 재시작이나 병합 통지 재전송 시 실제 기록과 대조해 집계를 복구한다. 보류 판정에 필요한 상태를 확인할 수 없으면 그 상태에 의존하는 행동만 보류한다.

감사 기준점은 실제로 검토한 마지막 병합 지점으로 옮긴다. 그 지점 이후의 병합은 다음 집계에 남겨, 감사 중 들어온 변경이 집계에서 빠지지 않도록 한다.

### 기술 스택과 확인 항목

기존 게이트웨이의 언어·런타임, 작업 실행 경로, 영속 저장소, 로그·보고 경로를 우선 사용한다. 아래 항목의 구체적인 이름과 연결 방식은 소스 확인 후 확정한다.

| 소스에서 확인할 것 | 설계에 반영할 내용 |
|---|---|
| 프로세스 진입점과 기존 확장 방식 | 게이트를 시작할 위치, 저장소별 적용 범위, 규율을 불러오는 방식 |
| 작업 접수·위임·Git·PR 실행 경로 | 각 동작을 호출 직전에 확인할 수 있는 위치와 외부에서 실행되는 동작의 범위 |
| 작업 상태와 실행 이력의 저장 방식 | 경로 배정·해제, 결정 기록, 재시작 이후 감사 기준을 저장할 위치 |
| 기본 브랜치와 PR 호스팅·병합 방식 | 병합 기록 조회, 중복 통지 처리, 25번째 병합 직후 다음 병합을 확인할 위치 |

### 통합 검증 시나리오

- 기존 규칙의 명칭과 순서를 사용하는 설계가 별도 승인 없이 진행되고, 가정이 필요한 경우 기록에서 확인된다.
- 두 병렬 task가 겹치는 경로를 동시에 요청하면 한쪽만 배정되고, 관련 없는 작업은 진행한다.
- 범위 밖 파일 이동과 타 모듈 내부 참조가 각각 커밋 또는 PR 검토에서 발견된다.
- 누적 24개 상태에서 PR 두 개가 동시에 병합을 요청하면, 첫 병합으로 감사가 발동하고 다음 일반 병합은 현재 상태를 다시 확인한다.
- 병합 직후 게이트웨이가 재시작하거나 통지가 중복돼도 PR을 한 번만 집계한다. 감사 수정 PR과 영향 범위 밖 PR은 각자 적용되는 조건에 따라 진행한다.

## 4. 게이트가 적용할 작업 규율

PRD 작성·개정, task 분할·위임, 커밋, PR 생성·병합 전과 PR 누적 감사 시점에 아래의 해당 항목을 적용한다.

### 설계 전

소유주가 지정한 첫 작업의 문서·PR·커밋 중 확인할 수 있는 기록을 읽는다. **무엇을 왜 했는지, 어디까지 했는지, 어떤 선행 작업 때문에 그 순서로 진행했는지**를 파악하고 후속 설계에 반영한다.

- 설계명, 문서명·경로, task 식별자, 브랜치명, 검토·PR 절차는 현재 저장소 지침을 따른다. 요구사항과 모듈 계약은 현재 승인된 PRD·명세에서 확인한다. 시범 기록은 작업의 맥락을 이해하고 현행 규칙이 열어 둔 부분을 해석하는 데 쓴다.
- 시범에 등장한 개별 이름과 순서는 그 작업의 기록이다. 후속 작업의 이름과 순서는 적용 대상 저장소의 명명 규칙과 실제 의존 관계로 결정한다. 자료가 부족하거나 충돌하면 그 판단에 아래 기준을 적용하고, 영향을 받지 않는 설계는 이어간다.

### 자율 결정과 기록

- 요청 범위에서 되돌릴 수 있는 결정은 에이전트가 내리고 진행한다. 근거가 부족해도 영향이 작으면 합리적인 가정을 택하고, 그 가정이 틀렸을 때 바뀌는 부분을 기록한다.
- 기존 승인 규칙이 발동하거나, 상충하는 명시 요구를 해결해야 하거나, 요청 범위를 바꾸거나 되돌리기 어려운 조치에 별도 권한이 필요하면 그 결정만 사용자에게 넘긴다. 충돌하는 요구와 필요한 결정, 선택에 따른 영향을 함께 보여준다.
- 사용자가 바꾸면 결과나 후속 작업이 달라지는 결정은 결정할 때 기록한다. 설계 경계, 후속 작업 순서, 범위 변경, 검증을 좌우하는 가정이 여기에 해당한다. **무엇을 정했는지 → 근거와 가정 → 영향 → 바꾸려면 어디를 수정할지** 순으로 한두 줄이면 충분하다.
- 결정은 저장소의 기존 결정 문서나 작업 기록에 남긴다. 별도 결정 문서가 필요한 경우 저장소의 명명·배치 규칙을 따른다. 진행·완료 보고에는 사용자가 검토할 만한 결정과 기록 위치를 짧게 표시한다. 사용자가 결정을 바꾸면 기존 기록에 수정 내용과 이유를 덧붙이고 관련 작업에 반영한다.

### 분할·위임 전

- 각 task의 목적, 변경할 모듈과 경로, 선행 작업, 완료 조건을 정한다. 위임문에는 작업 위치, 기준 커밋, 변경 범위, 검증 방법을 전달한다. 저장소에 기존 양식이 있으면 활용한다.
- 병렬 task는 쓰기 경로가 겹치지 않게 배정하고 각자 전용 Git worktree를 사용한다. 상위·하위 경로도 비교한다. 공유 파일은 한 task에 맡기거나 변경 순서를 정한다. 다른 모듈과는 공개 인터페이스로 연결하고, 공유 계약은 저장소의 기존 변경 절차를 따른다.
- **동시 배정 시에는 한 곳에서 중복 확인과 기록을 함께 처리한다.** 기존 작업 목록을 쓴다. 여러 에이전트가 동시에 그 목록을 갱신할 수 있다면 기존 담당자 또는 직렬화된 배정 경로를 사용한다. 경로를 추가해야 할 때는 추가분만 다시 확인하고, 작업이 끝나거나 취소되면 배정을 해제한다.

### 커밋·PR·병합 전

| 시점 | 확인할 내용 |
|---|---|
| 커밋 전 | 스테이징된 변경이 맡은 경로에 들어가는지 확인한다. 파일 이동은 이전과 새 경로를 모두 확인하고, 변경에 필요한 기존 검사를 실행한다. |
| PR 생성 전 | 대상 브랜치와 비교한 전체 변경, 선행 작업, 완료 조건을 확인한다. 모듈 간 참조를 바꿨다면 공개 인터페이스를 통하는지 기존 의존성 검사로 확인하거나 관련 diff를 검토한다. 기존 PR 양식을 사용한다. |
| 병합 직전 | 기존 승인·검사 조건과 현재 감사 상태를 확인한다. 감사 상태 확인에는 병합 요청 당시의 결과 대신 병합 직전의 값을 쓴다. |

충돌이나 검증 실패가 발견되면 해당 변경만 보류한다. 범위나 관련 상태가 바뀌면 영향받는 항목만 다시 확인한다.

### PR 누적 감사

1. 직전 감사 이후 기본 브랜치에 병합된 고유 PR이 **25개**에 도달하면 감사를 진행한다. 첫 집계는 이 규칙을 도입한 시점부터다. 병합 기록으로 세고 여러 worktree가 기준점을 공유한다.
2. 25번째 병합을 확인한 뒤 다음 일반 PR을 병합하기 전에 감사 상태를 공유한다. 병합이 동시에 일어날 수 있으면 기존 병합 대기열이나 병합 담당자를 통해 집계 확인과 병합 순서를 한 곳에서 처리한다.
3. 활성 에이전트는 다음 커밋 또는 PR 전에 자기 영역을 점검한다. 경로 침범, 타 모듈 내부 참조·순환 의존, 공유 계약 위반, 공용 파일에 집중된 변경을 살펴보고 발견 사항만 근거 PR이나 경로와 함께 남긴다. 영향받지 않는 작업은 계속한다. 감사에 착수해 차단 범위를 확인할 때까지 일반 PR의 병합만 잠시 보류한다.
4. 차단 범위가 확인되면 그 범위의 변경만 병합을 보류한다. 감사에서 범위가 확인된 수정 PR은 기존 검증·승인 절차를 거쳐 병합할 수 있다. 감사가 끝나면 검토를 마친 마지막 병합 지점을 다음 집계 기준으로 기록한다.
